# CI and Security Hardening

How continuous integration works for this repository, what it enforces,
and how to run every check locally before pushing. Companion documents:
[11-GIT-WORKFLOW.md](11-GIT-WORKFLOW.md) (branching), [12-DEPLOYMENT.md](12-DEPLOYMENT.md)
(production deployment), [SECURITY.md](../SECURITY.md) (security policy).

## 1. Status

CI exists and runs locally rehearsed (every check in this document was
executed on a development machine before being committed). The workflow
targets GitHub Actions — the repository's actual hosting platform — with
`.github/workflows/ci.yml`. CI has not yet been observed running on the
remote platform; the checks and their local equivalents are identical.

## 2. What CI runs

One workflow, four jobs, all independent and parallel:

| Job | Checks | Where |
|---|---|---|
| **Backend** | byte-compilation (`compileall`), dependency consistency (`pip check`), full pytest suite | `apps/api` |
| **Frontend** | ESLint, Vitest, `next build` production build | `apps/web` |
| **Docker** | both compose configs validate, both application images build, worker entrypoint imports in the API image, both Caddyfiles pass `caddy validate` | repository root |
| **Security** | gitleaks (full git history), pip-audit (Python dependency closure), npm audit (production deps, critical gate), bandit (static analysis) | mixed |

Design notes:

- **Python 3.12 / Node 22, one of each** — the versions the project
  targets (and Node 22 matches the web Dockerfile base image). No
  version matrices; a green check means *the* supported stack passes.
- **Backend tests need no services.** The suite runs on in-memory SQLite
  and fakeredis (see `apps/api/tests/conftest.py`) — no database or
  Redis containers in CI, nothing mocked that was a real integration
  test before.
- **Python dependencies come from `pyproject.toml` alone** (`pip install
  --group dev -e .`, with pip upgraded first because PEP 735
  dependency-groups support needs pip ≥ 25.1). There is deliberately no
  second Python package manager.
- **Frontend installs use `npm ci`** — the committed lockfile's exact
  state, never `npm install`.
- **Docker validation uses the committed `.env.prod.example`** — fake,
  public-safe values. CI never sees real credentials and never deploys
  anything; deployment is an operator action (docs/12 §6).

## 3. Required checks

All four jobs are required: a branch with any red check does not merge.
There are no informational-only jobs — if a check is worth running, its
failure means something. The expected branch-protection setup that makes
this real on the platform is described in §9.

## 4. Failure policy

**CI fails on:**

- any test failure (backend or frontend)
- lint errors and production build errors
- invalid compose files, failing Docker image builds, failing Caddyfile
  syntax, a broken worker entrypoint
- secrets detected by gitleaks (in the working tree *or* any commit)
- Python dependency vulnerabilities found by pip-audit (any severity)
- frontend production-dependency vulnerabilities at **critical** severity
- bandit findings at medium severity or higher
- security regression test failures (§10)

**CI does not fail on:**

- warnings that do not affect correctness (deprecation notices, etc.)
- low-severity informational static-analysis findings (bandit runs at
  `-ll`; the codebase has a handful of accepted low findings)
- known, documented dependency exceptions (§6)

Changing this policy — raising or lowering any gate — is a deliberate,
reviewed change to this file and the workflow, never a quiet edit to
make a build green.

## 5. Security tools and why these

Exactly one tool per concern, each calibrated to this codebase:

- **Secret scanning: [gitleaks](https://github.com/gitleaks/gitleaks)
  8.28.0**, pinned binary download verified by SHA-256 (`ci.yml` carries
  the digest), run over the **full git history**
  (`fetch-depth: 0`). No allowlist file is needed — the repository is
  clean; if gitleaks ever fires, that is a real finding, not noise.
- **Python dependency audit: pip-audit** against the project's resolved
  dependency closure. The closure is frozen *before* pip-audit is
  installed, so pip-audit's own tooling dependencies are never part of
  the audit, and pip itself is upgraded first (an old bundled pip is
  otherwise the only "vulnerability" a fresh environment has).
- **Frontend dependency audit: `npm audit --omit=dev
  --audit-level=critical`** — production dependencies only. See §6 for
  why the gate is critical and not high.
- **Static security analysis: bandit 1.9.4** at `-ll` (medium+), the
  level calibrated for this codebase; findings below that threshold are
  informational noise here. The single accepted exception is
  `# nosec B104` on the API's `0.0.0.0` bind in
  `apps/api/app/core/config.py` — the comment there explains why binding
  all interfaces is required in the container runtime (exposure is
  controlled by Docker networking, not the bind).

## 6. Dependency audit exceptions

The current, complete list of accepted findings:

- **postcss (via `next` ^15.0.0), 1 moderate + 1 high vulnerability.**
  The reported postcss issues (XSS via unescaped `</style>` in input,
  arbitrary file read via `sourceMappingURL`, path traversal in source
  map auto-loading) all require attacker-controlled CSS as input. This
  application processes only its own CSS at build time; there is no
  production runtime path where untrusted CSS reaches postcss. The only
  remediation is a SemVer-major upgrade to `next@16.3.4`, which is out
  of scope for routine CI work and must be a deliberate, individually
  evaluated upgrade (see SECURITY.md "Dependency Update Expectations").

Nothing is suppressed via tooling configuration; the exception lives in
this document and in the audit severity gate. When a fix lands in a
compatible version, the exception paragraph should be deleted.

## 7. CI needs no secrets

Every job runs with `permissions: contents: read` — read-only access to
the repository and nothing else. No workflow step references
`${{ secrets.* }}`, no job uses a GitHub environment, and the workflow
triggers on `pull_request` (never `pull_request_target`). Consequence:
**untrusted fork pull requests run the exact same pipeline with zero
access to anything sensitive.** Keep it that way — a future job that
needs a secret should first have to justify why, and `pull_request`
fork runs should still get along without it.

## 8. Supply chain and caching

- **Third-party actions are pinned to immutable commit SHAs** (with the
  human-readable version in a comment), so a compromised or retagged
  upstream release cannot change what executes here. Only official
  `actions/*` are used; no third-party actions at all.
- **Pip caching** is the pip download cache (wheels) keyed on
  `apps/api/pyproject.toml`; **npm caching** is npm's own tarball cache
  keyed on the lockfile. Neither caches a virtual environment nor
  `node_modules`, so a corrupted cache can only slow a build, never hide
  a broken dependency set.

## 9. Branch protection expectations

CI can only be a gate if the platform enforces it. Repository operators
should configure `main` (in the hosting platform's settings, not by
automation) to:

1. require pull requests (no direct pushes to `main`)
2. require all four CI jobs to pass before merge
3. disallow force pushes and history deletion
4. delete branches after merge

Day-to-day flow (docs/11): short-lived feature branches, merge commits
with `--no-ff`, branch deleted after merge.

## 10. Security regression tests

`apps/api/tests/test_compose_security.py` asserts the deployment
security posture at the configuration level — the same class of
regression as a failing unit test:

- only the Caddy proxy publishes host ports (80/443); postgres, redis,
  api, worker, and web publish none
- internal services attach only to the internal network
- no privileged containers, host networking/PID/IPC, or Docker socket
  mounts; the only bind mount is the read-only Caddyfile
- every service: `no-new-privileges`, read-only root filesystem,
  `cap_drop: ALL` — capability *additions* are pinned to the documented
  minimal sets (postgres: CHOWN/DAC_OVERRIDE/FOWNER/SETGID/SETUID for
  the official entrypoint; caddy: NET_BIND_SERVICE to bind 80/443 as
  root in the stock image)
- application Dockerfiles end on a non-root `USER`

Application-level security properties are covered by the existing suite
(fail-closed production config: `test_config_hardening.py`; auth/401/403
contracts: `test_api_auth.py` / `test_api_authz.py`; secret masking and
metrics policy: `test_observability.py`) — deliberately not duplicated.

The runtime counterpart — that the hardened stack actually *runs* — was
validated by the full local deployment simulation (Task 5.13, same
procedure as docs/12 §16): deploy, create a user, 18/18 verification
checks through the public edge including login, stack recreation with
data persistence, plus direct probes (`Read-only file system` on write,
`CapEff: 0`, `NoNewPrivs: 1`).

## 11. Container hardening summary

All six production services (docker-compose.prod.yml) run with
`read_only: true` + tmpfs for the paths that must stay writable
(`/tmp`; postgres's socket dir; Next.js's `/app/.next/cache` runtime
data cache), `cap_drop: ALL` plus the documented minimal additions, and
`no-new-privileges:true`. Redis runs as its image user `999:999`
(skipping the root+gosu entrypoint path). The API/worker/web images
already run as non-root users (their Dockerfiles). Caddy's stock image
runs as root and binds 80/443, hence its single `NET_BIND_SERVICE`
capability; a fully non-root caddy would additionally need volume
ownership handling for its data/config volumes and is not worth the
complexity here.

Everything above was validated by actually running the stack (§10) —
hardening that breaks a runtime is worse than no hardening.

## 12. Running CI locally

Every CI check has a local equivalent (run from the repository root):

```bash
# Backend (from apps/api, in the project venv)
python -m pip install --upgrade pip && python -m pip install --group dev -e .
python -m compileall -q app tests worker_healthcheck.py
python -m pip check
python -m pytest                     # PYTHONUTF8=1 on Windows

# Frontend (from apps/web)
npm ci
npm run lint
npm test
npm run build

# Docker
docker compose -f docker-compose.yml config -q
docker compose --env-file .env.prod.example -f docker-compose.prod.yml config -q
docker compose --env-file .env.prod.example -f docker-compose.prod.yml build api web
docker compose --env-file .env.prod.example -f docker-compose.prod.yml \
  run --rm --no-deps api python -c \
  "from app.worker.worker import WorkerSettings; assert 'redis_settings' in WorkerSettings.__dict__"
docker run --rm -e WEB_DOMAIN=localhost \
  -v "$(pwd)/deploy/Caddyfile:/etc/caddy/Caddyfile:ro" \
  caddy:2 caddy validate --config /etc/caddy/Caddyfile
# (repeat with deploy/Caddyfile.local; WEB_DOMAIN is a fake value — the
# {$WEB_DOMAIN} site address just has to expand to something non-empty)

# Security (from apps/api)
python -m pip install bandit==1.9.4
bandit -r app worker_healthcheck.py -ll --quiet
# pip-audit (fresh scratch venv recommended; upgrade pip first)
python -m pip install pip-audit && pip-audit -r frozen-requirements.txt
# npm audit (from apps/web)
npm audit --omit=dev --audit-level=critical
```

gitleaks: download the pinned release from the gitleaks GitHub releases
page (verify the digest against `ci.yml`), then `gitleaks detect
--source . --redact`.

The compose security regression tests run with the rest of the backend
suite (`python -m pytest tests/test_compose_security.py`).

## 13. Interpreting failures

- **Gitleaks fires:** treat as a real leak until proven otherwise. Do
  not add an allowlist entry to make it pass. If a real secret was
  committed, rotate it — history rewriting does not un-leak it
  (SECURITY.md).
- **pip-audit fails:** read the advisory; upgrade the affected package
  within compatible bounds and re-run the suite. If no fixed version is
  compatible, document an exception in §6 with the reasoning — never
  silence the tool globally, never upgrade unrelated packages to
  "clean up" the report.
- **npm audit fails at critical:** same approach as pip-audit, scoped
  to production dependencies. High/moderate findings are currently
  governed by §6.
- **Bandit fails:** fix the finding or, if it is a genuine false
  positive for this codebase, suppress with a targeted
  `# nosec <rule>` **and a comment explaining why** (see the B104
  precedent in `apps/api/app/core/config.py`). Never blanket-disable a
  rule.
- **Compose security tests fail:** you probably changed the deployment
  topology. Either you weakened it (revert) or the change is deliberate
  (update the test and this document together, in the same PR).
